أولاً: جاهزية العمليات (Backend Readiness)

العمليات الخلفية (Logic) جاهزة بنسبة 100% لاستقبال ومعالجة المدفوعات عبر الطرق المعتمدة:

بوابات التقسيط

يتم التعامل مع Tabby و Tamara بسلاسة تامة مع تتبع الحالة التلقائي.

البطاقات الائتمانية

خدمة HyperPay مفعلة وتدعم مدى وVisa/MasterCard مع بروتوكولات الأمان العالية.

التوافق مع الـ API

تم توفير Endpoints موحدة لكل العمليات (جلب الطرق، البدء، التحقق).

ثانياً: جلب طرق الدفع المتوفرة (Getting Methods)

بدلاً من كتابة طرق الدفع يدوياً في التطبيق، قمنا بتوفير رابط برمجى مرن يعيد لك الطرق المتاحة وأيقوناتها:

نقطة النهاية: GET /api/payment/methods
المهمة: تحديث قائمة الدفع في التطبيق ديناميكياً (مثلاً لو أوقفت Tabby مؤقتاً سيختفي تلقائياً).
{ "error": false, "data": [ { "key": "mada", "name": "مدى", "type": "card", "icon": "..." }, { "key": "tabby", "name": "تابي (تقسيط)", "type": "redirect", "icon": "..." } ] }

ثالثاً: تسلسل العملية (The Sequence)

هذا هو التسلسل المنطقي والآمن لضمان عدم ضياع أي حجز أو دفع:

graph TD A[1. اختيار الرحلة] --> B[2. إنشاء حجز PNR موقت] B --> C{3. هل تم الحجز بنجاح؟} C -- نعم --> D[4. طلب الـ Payment URL / Checkout ID] C -- لا --> E[إظهار خطأ للمستخدم] D --> F[5. عملية الدفع في التطبيق] F --> G[6. التحقق من نجاح الدفع Verify] G --> H{7. هل الدفع مكتمل؟} H -- نعم --> I[8. طلب قطع التذكرة Order Ticket] H -- لا --> J[تنبيه المستخدم بفشل العملية] I --> K[9. إصدار التذكرة والفاتورة PDF]

الإجابة على سؤالك: نعم، يتم الحجز (PNR) أولاً لضمان وجود مقاعد، ثم يتم الدفع، وبمجرد نجاح الدفع يتم طلب إصدار التذكرة النهائية.
