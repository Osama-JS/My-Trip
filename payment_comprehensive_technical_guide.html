تكامل بوابات الدفع (HyperPay, Tabby, Tamara)

دليل شامل للمطورين حول معمارية الدفع الموحدة ورحلة المستخدم

1. استراتيجية قطع التذكرة (The Strategy)

يعتمد النظام استراتيجية "الحجز المؤقت أولاً" لضمان حماية المقاعد والسعر قبل التزام العميل بالدفع:

graph LR A[البحث] --> B[تأكيد السعر] B --> C[إنشاء PNR] C --> D[تهيئة الدفع] D --> E[التحقق من الدفع] E --> F[إصدار التذكرة Order] style C fill:#f9f,stroke:#333,stroke-width:2px style F fill:#00ff00,stroke:#333,stroke-width:2px

لماذا هذا الترتيب؟ لضمان عدم قيام العميل بالدفع مقابل رحلة أصبحت "غير متاحة" فجأة. الحجز (PNR) يحجز المقاعد لفترة زمنية محددة (Time Limit) تكفي لإتمام عملية الدفع.

2. ديناميكية اختيار الوسيلة (Gateway Selection)

نحن لا نثبت وسائل الدفع في التطبيق. بل نطلبها من السيرفر لتكون قابلة للتغيير في أي وقت:

GET /api/payment/methods

يستخدم التطبيق هذه القائمة لعرض الخيارات (مدى، فيزا، تابي، تمارا) مع أيقوناتها المحدثة.

3. دالة التهيئة الموحدة (Unified Initiate)

نقطة دخول واحدة لكافة البوابات. لاحظ أن callback_url أصبح يُدار بواسطة السيرفر لضمان الموثوقية وتوحيد تجربة العودة:

POST /api/payment/initiate

{ "amount": 1250.0, "payment_type": "tabby", "order_id": "PNR_123456", // لم يعد ارسال callback_url من التطبيق ضرورياً (السيرفر يحدده تلقائياً) "email": "customer@email.com", "phone": "9665XXXXXXXX" }

في HyperPay

يعيد السيرفر checkout_id فقط. يقوم التطبيق باستخدام الـ SDK أو WebView لعرض نموذج البطاقة البنكية.

في Tabby / Tamara

يعيد السيرفر checkout_url. يجب على التطبيق فتح هذا الرابط في WebView فوراً. السيرفر سيوجه بوابة الدفع للعودة لصفحة انتظار خاصة به.

4. رحلة العودة والمعالجة (Server-Side Landing Page)

بدلاً من العودة المباشرة للتطبيق عبر Deep Link، قمنا بتحسين العملية لتتم عبر السيرفر أولاً لضمان استقرار جلسة الدفع وتسهيل عمل التطبيق:

الاستراتيجية الجديدة: بوابة الدفع تعود لصفحة /api/payment/callback على السيرفر، والتطبيق يراقب الـ URL لاستخلاص الـ ID.

تسلسل العودة الجديد:

  1. العميل يكمل الدفع في WebView.
  2. بوابة الدفع تعيد العميل لرابط السيرفر: https://your-api.com/api/payment/callback?payment_id=XXX.
  3. تظهر للعميل صفحة "جاري المعالجة" احترافية داخل الـ WebView.
  4. دور التطبيق: يقوم بمراقبة (Intercept) رابط الـ WebView. عندما يجد أن الرابط يحتوي كـ نص على /payment/callback، يقوم بقراءة الـ payment_id من الـ Query Parameters وإغلاق الـ WebView.
  5. يقوم التطبيق بطلب الـ /verify باستخدام الـ ID الذي استخلصه لتأكيد العملية رسمياً.

5. مقارنة المعالجة التقنية

الخاصية هايبر باي (البطاقات) تابي و تمارا (التقسيط)
الرد من التهيئة Checkout ID Checkout URL (رابط)
طريقة العرض نموذج بطاقة (In-App) إعادة توجيه (External/WebView)
متطلبات العميل البريد (اختياري) البريد، الهاتف، العنوان (إجباري)
التحقق Verify عبر Checkout ID عبر Payment ID (من رابط العودة)

6. قائمة التحقق للمطور (Checklist)

  • [ ] استدعاء /methods لبناء خيارات الدفع.
  • [ ] التأكد من وجود PNR ناجح قبل طلب الدفع.
  • [ ] إرسال بيانات العميل كاملة عند اختيار تابي/تمارا لتجنب الرفض.
  • [ ] تعريف Deep Link في ملف (AndroidManifest.xml / Info.plist) للتطبيق.
  • [ ] استدعاء /verify فور العودة من بوابة الدفع.
  • [ ] استدعاء /order-ticket فقط بعد أن يكون رد الـ verify بنجاح.
